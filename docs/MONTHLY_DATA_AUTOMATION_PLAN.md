# 月度数据自动更新执行方案

> 状态：`current_execution_baseline / approved_plan`
> 生效日期：2026-08-26；最近状态复核：2026-08-27
> 适用范围：后续所有月度数据自动更新的设计、修改、演练、部署、运行复核和故障处理。
> 当前实施状态：`automation_disabled`。本方案不是部署、发布或生产开关已启用的证据。

## 1. 作用与边界

本方案把后续工作统一到一条可执行、可核验的流程上，重点解决“每20分钟发现”不能只停留在Cron表达式的问题。

它不替代下列现有权威文件：

- 官方来源、字段、解析和数据正确性，遵循 [数据契约](DATA_CONTRACT.md)。
- 远程数据、缓存、回滚、候选和权限规则，遵循 [小程序每月自动数据更新](MINIPROGRAM_DATA_UPDATE.md)。
- 生产自动发布的全部硬门槛，只以 [自动更新启用清单](AUTOMATION_ACTIVATION_CHECKLIST.md) 为准。
- 当前实现与验证差距，只在 [实施状态登记](IMPLEMENTATION_STATUS.md) 登记。

发生冲突时，按 `AGENTS.md` 的优先级处理；本方案不得放宽任何数据校验、生产权限或发布门槛。发现任务永远不得直接发布正式数据。

## 2. 严格20分钟发现的定义

具体的北京时间、起止时段和Cron表达式仍只在 `MINIPROGRAM_DATA_UPDATE.md` 维护。本方案要求当前时间表中的27个发现时段都满足以下条件：

1. 每个时段有唯一的 `slot_id`、计划开始时间、实际开始时间、结束时间、结果和重试记录。
2. 首次只读发现必须在计划时段后2分钟内真正开始访问发现逻辑，而不是只创建一个排队任务。
3. 超过2分钟才开始，即使后来成功，也必须记录为 `late`，不能当作准时完成。
4. 一个时段重复触发只能得到同一条时段记录；重复事件不能制造第二次业务处理。
5. 最后一个发现时段到每日截止时间之间只允许完成该时段的有限重试；截止后不再启动新的发现请求，只记录结果和告警。

这里的“严格”是可验证的服务规则，不声称公共云或GitHub能够保证秒级绝对准点。任何迟到、漏跑或官方来源超时都必须留下失败证据，不能被后续成功静默覆盖。

## 3. 目标流程

```text
同步官方日程
  -> 时段控制器
  -> 只读发现
  -> 不可变观察报告
  -> 候选准备与数据门禁
  -> 受保护发布
  -> 发布后守卫与回滚
```

### 3.1 同步官方日程

- 日程只决定何时检查，不是正式数据来源。
- 月度与年度官方日程必须继续交叉核对；冲突、缺失或无法验证时停止并报告。
- 日程同步与正式页面发现职责分开，不能把日程同步任务误算为一次发现完成。

### 3.2 时段控制器

- 腾讯云定时器按分钟唤醒控制器；控制器按北京时间计算当前是否到达应执行的20分钟时段。
- 控制器在CloudBase数据库中以事务领取时段，并使用可过期租约、防重和重试次数，避免并发或中断后永久占用时段。
- 时段状态至少区分：`pending`、`started`、`succeeded`、`retrying`、`failed`、`late`、`expired`。领取成功不等于发现已经开始或已经成功。
- `monthlyDataWatchdog` 现已是严格时段的独立控制器和只读发现执行器：它按北京时间领取时段、直接完成发现并写入观察记录。GitHub仅保留为审计和备用信号，不再被当作准时发现的依据。此处替换部署前“只检查GitHub运行”的历史描述，不改变20分钟时段、权限边界或生产发布关闭状态。

### 3.3 只读发现

- 腾讯云只读发现执行器是严格时段的主执行者，直接运行与GitHub相同的官方来源白名单、日程判断和月份比较逻辑。
- 发现逻辑必须由单一、可测试的共享模块提供，不能维护两套会逐渐不同的页面识别规则。
- 当前正式月份只能以生产云端 `current.json` 的只读回读为准；仓库内Web清单、历史报告或待发布状态只能交叉核验。
- 每次发现生成非敏感的观察报告。发现新月份只产生固定身份的交接，不写正式数据、不改变正式指针、不更新小程序页面。
- 每次成功观察还必须写入按 `sha256(slot_id)` 固定命名的非业务观察对象；GitHub 只能通过现有只读监测身份读取该对象，不能读取 CloudBase 数据库或申请生产写权限。

### 3.4 GitHub的职责

- GitHub保留为代码审计、可复现报告、人工重放和备用信号，不再作为严格时段的唯一时钟。
- GitHub定时任务迟到、漏投或排队时，必须由时段控制器记录并处理；晚到的GitHub运行不能冲掉已记录的 `late` 或 `failed` 状态。
- 任何备用补发仍使用同一 `slot_id` 和同一发现身份，避免形成触发风暴。
- GitHub 候选门禁必须同时验证腾讯云观察对象的 `observation_id`、`payload_sha256`、`timing_status`、指针月份、官方 URL、幂等键和 `handoff_identity`。缺失、迟到、失败、过期或哈希冲突时必须失败关闭；GitHub 自己的 `handoff.json` 不能替代腾讯云证据。

### 3.5 候选、发布和监测

- 发现后才允许进入候选准备；候选必须使用稳定的发布身份、不可变原始来源和可恢复状态机。
- 相同官方原文、代码提交和配置必须得到相同候选字节。检查时间、运行ID和重试次数只能进入审计字段，不能改变候选身份。
- 候选、发布、回滚和状态部署继续遵循现有独立门禁。任一门禁失败时，正式 `current.json` 保持原字节不变。
- 发布后监测只读回读正式指针、清单、完整70城数据和安全回退状态；问题进入告警或人工隔离，不能通过重跑绕过门禁。
- 待发布恢复必须重新读取并核对同一腾讯云观察对象，不能只相信仓库中持久化的候选字段；对象身份变化或不存在时停止恢复。

## 4. 网络、重试与故障处理

1. 官方日程、发布列表和正式页面正文的连接、响应头、正文读取、长度校验和哈希计算必须属于同一次尝试。
2. 每次请求都有明确超时；确认前一次请求已终止后才可以重试，避免重叠访问和重复处理。
3. 重试只在本时段允许的时间内进行，并使用同一 `slot_id`。达到截止时间仍失败时标记为 `failed` 或 `expired`，等待人工处理或下一个合法时段。
4. 官方页面返回验证码、拦截页、结构变化、来源冲突、缺表、缺城或月份冲突时，按数据契约失败关闭，不能把错误页面当作官方数据。
5. GitHub、CloudBase数据库、只读生产指针或网络任一依赖不可用时，保留最后一个安全数据版本，写入原因和时间；绝不降级为无校验发布。
6. D19未关闭前，现有运行摘要和失败状态只能作为有限告警信号，不得称为已经完成无人值守通知闭环。

## 5. 权限与安全边界

- 发现执行器只拥有访问官方公开页面、写自身时段记录/非业务观察对象和读取已授权生产指针所需的最小权限；没有生产数据写权限。GitHub 只读身份只能读取观察对象和既有正式只读对象。
- 看门狗的GitHub令牌只允许读取Actions运行并在需要时触发固定发现工作流；不得拥有Contents、Secrets、Variables、Administration、Deployments或生产云端权限。
- 令牌、密钥、验证码和正式数据写凭据不得写入源码、文档、日志、Artifact或聊天。
- `AUTOMATIC_RELEASE_ENABLED` 必须保持 `false`，`PRODUCTION_RELEASE_AUTHORIZED` 必须保持 `false` 或未设置，直到启用清单全部适用项有当前可复查通过证据且维护人再次明确授权。
- 只读发现、重试、看门狗、日程同步和观察报告均不得借任何例外写正式数据或开启发布。

## 6. 实施顺序

### 阶段A：本地实现与测试

1. 提取共享的只读发现模块，供GitHub和腾讯云执行器共同使用。
2. 建立时段记录、租约、幂等领取和失败恢复状态机。
3. 将日程同步、时段控制、发现执行和GitHub审计拆分为清晰职责。
4. 建立 CloudBase 观察对象的确定性命名、写后回读和 GitHub 只读消费门禁。
5. 保留现有数据门禁和生产双开关，不在本阶段部署或打开任何生产写入能力。

### 阶段B：隔离云端演练

1. 在不含生产写凭据的云函数中部署时段控制器和只读发现执行器。
2. 先以dry-run记录所有时段，不触发备用GitHub工作流。
3. 模拟定时漏投、GitHub排队、请求超时、数据库领取失败和重复事件，验证时段不会丢失、重复或永久锁死。
4. 自2026-08-28起，严格发现的有限观察门槛改为连续10个计划发现时段均有可审计记录。每个时段都必须单次、`succeeded`、`timing_status=on_time`，并与唯一观察对象的`slot_id`、载荷哈希和交接身份一致；`calendar`和`discovery-observation`记录不得计入10次。任一迟到、失败、重复、重试遗留或缺记录必须先定位并修复，再从新的连续时段重新计数。此前“连续3个完整发现窗口”规则自本日期起仅保留为历史记录，不再作为本方案的门槛。

### 阶段C：启用只读保障

1. 取得对云函数和定时器的明确部署授权后，才将经过演练的只读补救从dry-run切为实际执行。
2. 现场回读定时器、时区、函数版本、最小权限和最新运行记录，确认严格时段规则已生效。
3. GitHub仍仅作为审计和备用重放；这一阶段不等于自动发布已启用。

### 阶段D：发布能力的独立评估

只有在自动更新启用清单全部适用项通过、隔离验证和外部平台证据完成、两个生产开关分别被维护人明确授权后，才可单独评估正式自动发布。严格发现通过不能替代发布、回滚、真机或正式数据链路验收。

## 7. 每次变更必须遵循的规则

1. 先读取本方案、数据契约、数据更新规范、启用清单和实施状态，再确定修改范围。
2. 修改时段、时区、Cron、看门狗、发现逻辑、候选身份、解析器、门禁、云函数或工作流时，必须同步更新对应测试和本方案涉及的事实说明。
3. 修改 `apps/miniprogram/` 中会进入客户端构件的云函数源码、运行时校验、配置或内置数据时，必须按版本规范递增 `apps/miniprogram/config/version.js`，并同步到微信开发者工具目录；只改不进入客户端构件的云端脚本或文档时不触发版本递增。
4. 任何部署、令牌配置、定时器变更、生产开关修改、正式数据写入、回滚、上传或发布，都需要该次明确授权和现场回读；方案本身不构成授权。
5. 不得通过缩短时段、放宽超时、删减测试、重写历史证据或把历史成功记录当成当前通过来关闭问题。
6. 改变本方案本身时，必须同时说明变更原因、影响范围、替代或废止的规则、测试要求和生效日期；与权威文件冲突时先更新权威文件，不得仅修改本方案。

## 8. 验收与证据

严格20分钟发现的实现候选至少应提供以下当前证据：

- 覆盖全部27个时段的本地时区和时段计算测试，以及跨日、重复触发、租约过期和截止时间测试。
- GitHub漏投、排队和晚到时，CloudBase记录和处理结果的故障注入测试。
- 官方日程、发布列表和正文读取的完整重试与失败关闭测试。
- 同一官方原文多次触发只得到一个稳定发现身份、一个候选身份和可复查恢复路径的测试。
- GitHub 读取腾讯云观察对象、对象缺失/哈希冲突/迟到、月份或官方 URL 不一致时失败关闭的测试；候选和待发布恢复都必须绑定同一 `slot_id` 与观察身份。
- 隔离云端连续10个合格计划发现时段的实际记录、函数和时区现场回读，以及不含生产写入的权限核验。每日完整审计仍覆盖当天全部27个计划时段；27次不是本阶段的观察数量门槛，而是当天审计的完整性要求。
- 任何自动更新代码改动仍须按启用清单和数据更新规范完成适用的隔离回放、CI、数据校验、构建、开发者工具、真机和正式数据链路证据；不得用本方案替代这些门槛。

只有当前证据同时证明“按时开始”“正确完成”“失败可见”“没有生产越权”时，才能把严格发现记为已实现。否则应如实登记为 `partial`、`failed` 或 `not_tested`。

## 9. 当前结论与后续维护

截至2026-08-28，严格发现器源码、共享发现契约、时段状态机和 CloudBase 观察对象到 GitHub 的消费门禁已完成本地验证；当前工作区候选版本为 `v2.5.25`。`monthlyDataWatchdog` 已于2026-08-26 23:02（北京时间）用本轮源码重新部署，CloudBase 函数列表回读为 `Deployment completed`，手动调用返回只读 `strict_status=idle` 且 GitHub 补发路径关闭。该调用发生在当日窗口之后，不能作为完整窗口或准时发现证据。GitHub 只读监测身份已安全配置；现场验证证明它可读取正式 `current.json`，对不存在的观察对象得到 `NoSuchKey`，对正式发布目录得到 `AccessDenied`。2026-08-27的完整审计已提供连续27个单次、准时、成功且身份逐项一致的业务发现时段，覆盖新的10次观察门槛。生产发布开关继续关闭。严格20分钟发现的线上状态仍为 `deployed / passed_limited`；满足10次观察门槛只允许评估下一阶段，不能替代自动发布启用清单、发布、回滚、真机或正式数据链路验收。

### 2026-08-28 严格发现观察门槛变更

维护人要求将阶段B的有限观察门槛由“连续3个完整发现窗口”缩短为“连续10个计划发现时段”。本变更只缩短只读严格发现的观察数量，不改变27个每日计划时段、2分钟准时上限、单时段最多3次尝试、观察对象逐项核验、失败关闭、生产指针只读回读或两个生产发布开关必须保持关闭的规则。该决定自2026-08-28起持续有效；后续只有带日期、明确写出`supersedes`的维护人决定，同时更新本方案、实施状态和复核自动化后，才可再次调整。

后续每次月度自动更新工作都必须先按本方案判断当前阶段和授权范围，再执行对应步骤。发生新的运行异常、数据源变化或云平台规则变化时，先保留证据、停止危险操作，并在不放宽安全边界的前提下更新本方案及对应权威规范。
