## 结论

当前自动更新不是单点故障，而是以下三类问题叠加：

1. GitHub定时调度可能延迟或漏投。
2. 候选生成、保存和恢复契约彼此不一致，正常生成物会被自己的保存门槛拒绝。
3. 同一官方原文重复运行时，动态时间字段会生成同名但内容不同的候选，无法可靠重试。

## 代码与契约审计发现

### A01：候选持久化规则与候选生成规则冲突

- 生成流程会改变数据审计、标准化数据、Web数据和 `apps/miniprogram/data/snapshot.js`。
- 保存流程只允许原始来源证据和 `pending-auto-release.json`。
- 当前测试把生成流程的正常输出列为必须拒绝的路径。
- 结果是“候选全部检查通过”之后仍必然无法保存。

### A02：待发布恢复点建立得太晚

`pending-auto-release.json` 只有在抓取、审计、构建和测试全部完成后才创建。因此以下失败没有可恢复状态：

- 正文下载超时；
- 解析或审计中断；
- 候选保存失败；
- 测试阶段运行器中断。

当前恢复工作流还会从仓库已有Web数据重新生成候选，并未复用首次抓取原文和完整正常发布路径，不能保证恢复的是同一个候选。

### A03：已发布月份读取了错误的事实源

[`check-latest.ts`](../scripts/data/check-latest.ts) 使用仓库中的 `apps/web/public/data/manifest.json` 判断当前发布月份，而不是只读回读生产云端 `current.json`。如果云端已经切换成功、仓库收尾提交失败，后续检查仍会再次认定有新数据。

### A04：现有幂等键没有形成真正的去重

“幂等”表示同一件事重复执行不会产生第二份结果。当前流程虽然生成 `idempotency_key`，但没有在昂贵处理前按稳定身份查询 `preparing / ready / publishing / published / failed` 状态，也没有阻止多个发现运行重复构建同一月份。

当前幂等键还包含发布日程内容。同一份官方数据的两次运行因日程读取结果不同产生了不同键值；日程应该只决定“何时检查”，不应该改变“是不是同一份官方数据”。

### A05：同一原文会生成同名但内容不同的候选

两次候选使用相同官方原文：

- `source_raw_sha256`：`e809bb80b569d1445bad7d69e23348c1f26b24627225845ab76affb9bd487bcc`
- `dataset_version`：均为 `2026-07-5da3c160c5e3`

但输出身份不同：

| 字段 | 运行32324289710 | 运行32325188025 |
| --- | --- | --- |
| `source_dataset_version` | `2026-07-a471ea496771` | `2026-07-ddac312c42bf` |
| `manifest_sha256` | `3ed5ae0a79f23b5eed198310b9aad1a5a9dd138654a9f2b81412def81568a324` | `941abd5544fba8e89f7587d698bc22ca25cf2d52e6b6a42f37ef92c6ba94d3dc` |
| `bootstrap_sha256` | `926544302e54d603acc4153077bc6d2fc4341450da29fe79fb2cf2d5a99a2c62` | `bfde26caf59b5135fdf4234ec51df9a92a44026436d2bf3984c2f595d077e19a` |
| 生成时间 | `2026-08-20T02:22:56.801Z` | `2026-08-20T02:37:59.588Z` |

根因包括：

- `fetched_at` 进入标准记录和Web数据版本身份；
- `generated_at / generatedAt` 进入清单和完整数据包；
- 远程目录版本没有包含这些动态值。

如果第一次已经上传部分不可变候选、后续步骤失败，第二次重试会用同一个目录版本生成不同字节，随后被“不可变目录内容不同”保护永久拒绝。

### A06：工作流串行只能防并发，不能防重复

当前 `concurrency` 设置可以让正式发布任务排队，但后来的五分钟检查仍会各自发现同一月份并执行完整候选准备。它解决的是“不要同时写生产”，不是“同一数据只处理一次”。

### A07：文档与生产开关现场状态冲突

[`AUTOMATION_ACTIVATION_CHECKLIST.md`](AUTOMATION_ACTIVATION_CHECKLIST.md) 同时存在“2026-08-07已启用”和“门槛未完成、开关必须关闭”的描述；[`MINIPROGRAM_DATA_UPDATE.md`](MINIPROGRAM_DATA_UPDATE.md) 也保留了必须关闭的结论。审计现场两个开关却均为 `true`。后续修复必须同步厘清当前状态，不能让带日期的历史记录和当前操作结论混在一起。

## 推荐目标方案

### 1. 双触发、单处理

- GitHub定时任务继续作为主要触发器。
- 增加独立的腾讯云只读守护器；计划检查超过约7至10分钟仍未出现时，只补触发一次GitHub `workflow_dispatch`。
- 守护器只拥有检查运行和触发发现工作流的最小权限，不拥有腾讯云生产数据写权限，也不持有正式发布Secrets。
- GitHub定时和守护器可以重复触发，但都必须进入同一个稳定身份和状态机，因此只会处理一次。

### 2. 使用两层稳定身份

- `release_key = 统计月份 + 官方原文SHA-256`
- `candidate_id = release_key + 精确代码提交 + 候选清单摘要`

发布日程、检查时间、GitHub运行ID和重试次数只作为审计信息，不进入 `release_key`。

### 3. 建立真实状态机

建议状态为：

```text
preparing -> ready -> publishing -> published
                        |               |
                        +----> failed <-+
```

- 官方原文下载并验证哈希后，立即持久化原文、`release_key`、首次时间种子和 `preparing` 状态。
- 重复发现相同 `release_key` 时读取现有状态，不重复抓取和构建。
- `ready` 只表示候选门禁通过，不能推导为已发布。
- `publishing` 必须绑定精确候选、代码提交、GitHub运行和两个生产开关回读证据。
- `published` 必须以生产云端指针及数据包完整回读成功为准。

### 4. 候选只生成到工作目录和不可变Artifact

普通月度远程数据更新不应修改 `apps/miniprogram/data/snapshot.js`、Web正式发布目录或其他客户端源码。候选数据、清单、门禁和审计全部先生成到独立 `work/` 目录和不可变Artifact。

这样本次自动化修复不需要修改小程序页面，也不需要递增 `apps/miniprogram/config/version.js`。如果未来另行决定把新月份同步进小程序内置离线快照，那是单独的小程序发版候选，必须按版本规则处理。

### 5. 同一输入必须逐字节可复现

- 第一次创建 `preparing` 状态时固定时间种子。
- 后续恢复和重跑全部复用该时间种子。
- 官方原文身份字段不得因重新下载时间而改变。
- 相同原文、代码提交和配置必须生成逐文件相同的候选及相同SHA-256。
- 若已有同一 `candidate_id` 的远端目录，先完整回读并比较；完全相同视为幂等成功，不同则失败关闭。

### 6. 正常执行和恢复复用同一条代码路径

不要继续维护一套缩减版“恢复生成流程”。恢复入口应读取持久化状态和原始Artifact，从中断阶段继续执行正常流水线的相同步骤和门禁。

### 7. 统一网络重试边界

发布日程、正式发布列表和正式页面正文都采用完整请求重试：建立连接、读取响应头、读取完整正文、校验长度和计算SHA-256必须处在同一次尝试内。前一次请求必须确认取消后才能开始下一次，避免重叠请求。

### 8. 生产云端指针是唯一已发布事实源

发现流程在判断是否需要更新前，只读回读并验证生产云端 `current.json`。仓库Web数据、待发布状态和历史审计只能用于交叉核验，不能代替生产指针。

### 第4批：完整回放和重新启用评估

2. 核验36轮全部通过、正式指针和正式发布目录未触碰、回放期间两个生产开关均关闭。

4. 由维护人另行明确授权后，才可重新打开两个生产开关并分别回读。

## 最低验收标准

- 相同月份、相同官方原文重复触发至少5次，只产生一个 `release_key` 和一个候选。
- 同一候选独立生成两次，目录内每个文件逐字节相同，总清单SHA-256相同。
- 连接超时、响应头超时和正文读取超时均会按配置重试，且前一次请求不会与下一次重叠。
- 从每个关键阶段中断后都能恢复，不重新创造不同候选。
- 正式云端已经是目标月份时，仓库收尾状态即使落后也不会再次发布。
- GitHub定时任务漏投时，守护器在约定阈值内补触发一次，不形成触发风暴。
- 候选门禁、普通CI、两个正式开关、远端回读和安全回退目标任一失败时，正式指针保持原字节不变。
- 隔离测试不修改 `apps/miniprogram/` 客户端源码，不触发小程序版本递增。
- 一组36个月隔离回放全部通过后，仍不能自动推导为已重新启用；生产开关必须由维护人单独授权。
