## 一、设计结论

建议把本项目沉淀出的七步方法做成一个全局 Skill，供以后的代码项目每次开发时使用：

`定界 -> 盘点 -> 方案 -> 小步实施 -> 分层验证 -> 证据交付 -> 复盘固化`

小任务自动走简化流程；数据、安全、隐私、依赖、跨模块、云端、发布和不可恢复操作走完整流程。Skill 不替代项目自己的 `AGENTS.md`、产品规范和验收标准，也不自动修改业务代码或执行发布。

## 二、Skill 名称与描述

计划写入 `SKILL.md` 的名称和触发描述如下：

```yaml
---
name: verified-dev-workflow
description: >-
  在现有代码项目中执行可信、可复查的开发工作流。适用于用户要求检查、开发、修复、数据处理、安装配置或发布时：先读取项目规则并记录目标、允许和禁止范围及已有 Git 改动，再按风险选择简化或完整流程，小步实施、分层验证、检查越界，并准确区分已分析、已修改、已测试、已部署和已发布状态。用户提出“按我的工作流开发”“先检查再改”“保护已有改动”或“给出验证证据”等要求时使用。
---
```

该名称符合小写字母加连字符的要求；描述只说明何时使用和解决什么问题，不写死房产、小程序或其他单一领域规则。

## 三、用途、输入与输出

### 用途

- 每次代码项目开发、修复、检查、数据处理、安装配置或发布任务都可使用。
- 用户只咨询概念、翻译文字或处理与代码项目无关的简单事项时不触发。
- 项目内规则优先；Skill 负责读取和执行，不另建一套冲突规范。

### 默认输入

1. 项目位置。
2. 这次要达到的结果。
3. 允许修改的文件、目录或外部目标。
4. 明确禁止修改或禁止执行的事项。

如果成功标准、外部操作权限等信息可从项目中安全判断，Codex 自动补齐；只有缺失信息会明显改变产品结果、费用、数据、安全或可恢复性时，才一次询问最关键的问题。

### 默认输出

1. 当前真实结论和完成状态。
2. 面向用户说明做了什么。
3. 实际变化的文件、版本或配置。
4. 已完成的验证及其证据。
5. 用户接下来在哪里、点什么或运行什么。
6. 未验证范围、阻断项和适用时的回退办法。

## 四、执行路线

### 1. 只读路线

适用于“看看、检查、审核、比较、先出方案”。不得修改项目、安装依赖、运行会写文件的测试或执行外部操作。辅助记录必须写到项目目录之外，并用前后 Git 状态证明项目未变化。

### 2. 简化路线

适用于目标明确、范围很小、可本地恢复且不涉及数据口径、安全、隐私、共享契约、依赖、云端或发布的任务。仍必须完成任务卡、初始状态、针对性验证、范围检查和证据交付，但不机械执行所有高风险检查。

### 3. 完整路线

出现以下任一情况时使用：

- 官方数据、解析器、生成物、迁移或历史修订；
- 密钥、权限、隐私、安全、费用或外部账号；
- 新增或升级依赖、共享核心、跨平台契约；
- 大范围界面结构、关键交互或多端兼容；
- 云端写入、上传、审核、发布、回滚或删除；
- 修改范围不清、已有改动重叠或失败影响难以恢复。

完整路线要把实现、本地测试、构建、实际启动、设备、云端和发布平台按适用范围逐层验证。前一层证据不得代替后一层。

## 五、严格步骤与灵活步骤

### 每次都严格执行

- 先读取用户当前要求、项目 `AGENTS.md` 和相关权威规范。
- 修改前记录 Git 分支、提交、工作区状态和用户已有改动。
- 明确目标、允许范围、禁止范围、成功标准和外部操作权限。
- 保护已有改动；不得把原有脏文件算成本次修改，也不得覆盖它。
- 数据、安全、费用、范围和完成状态问题必须明确报告。
- 只使用证据支持的状态词，不从“代码已改”推断“已部署”或“已发布”。
- 任务结束前执行范围检查，并报告未验证事项。

### 可按现场情况调整

- 具体搜索、诊断、编辑和测试工具。
- 普通失败后的重试次数和安全替代方案。
- 测试的先后顺序和覆盖深度，但不得低于项目规则与风险要求。
- 是否需要把新教训写入测试、权威规范、验收标准或交接说明。

### 必须暂停并询问用户

- 需要扩大已授权修改范围。
- 两种方案会产生明显不同的产品结果。
- 删除、覆盖、付费、发布、生产写入或其他难以恢复的操作尚未明确授权。
- 缺少权限、账号或产品取舍，继续猜测会带来明显风险。

普通命令失败、可安全诊断的环境问题和不改变目标的替代实现，由 Codex 自动处理，不把排查工作推回给用户。

## 八、辅助 CLI 设计

脚本使用 Python 标准库和 `argparse`，由 Codex 通过 `uv run` 调用。三个子命令都强制要求 `--output`；长结果只写文件，终端只显示成功路径或简短错误；失败退出码为 1。

### 1. `start`：记录任务和初始状态

计划命令形状：

```powershell
uv run scripts/workflow_guard.py start `
  --project "C:\项目位置" `
  --goal "这次要达到的结果" `
  --task-type fix `
  --route simple `
  --allow "README.md" `
  --deny "src\payment" `
  --success "README中的启动步骤准确" `
  --output "C:\临时证据\start.json"
```

参数设计：

| 参数 | 规则 |
| --- | --- |
| `--project` | 必填；解析为绝对项目路径 |
| `--goal` | 必填；记录用户真正要得到的结果 |
| `--task-type` | 必填；`readonly`、`develop`、`fix`、`data`、`install` 或 `release` |
| `--route` | 必填；`readonly`、`simple` 或 `full`，由 Skill 按风险选择 |
| `--allow` | 可重复；非只读任务至少一个；使用项目相对路径或明确的目标文件 |
| `--deny` | 可重复；禁止范围，优先级高于允许范围 |
| `--success` | 至少一个；可复查的成功标准 |
| `--output` | 必填；建议放在项目外的临时证据目录 |

输出记录包括：项目真实路径、时间、Git 根目录、分支、提交、初始状态、已有改动、允许和禁止范围、任务路线及成功标准。对已有修改和未跟踪文件只保存路径、状态、大小和 SHA-256 指纹，不复制文件内容，避免把隐私或密钥写进证据。

如果不是 Git 项目，Skill 仍可执行高层流程，但 CLI 必须标记 `guard_level: limited`，不得声称已完成全项目越界检查，也不得擅自初始化 Git。

### 2. `scope-check`：检查是否越界或碰到已有改动

计划命令形状：

```powershell
uv run scripts/workflow_guard.py scope-check `
  --baseline "C:\临时证据\start.json" `
  --output "C:\临时证据\scope.json"
```

该命令重新读取 Git 状态和文件指纹，并分类为：

- 用户原有改动且内容未变化；
- 本次新增且位于允许范围；
- 本次新增但超出允许范围；
- 禁止范围内的变化；
- 原有脏文件又被本次改动；
- 无法可靠判断的变化。

路径先规范化为项目相对路径；目录规则覆盖其子项；禁止规则优先；只读路线出现任何项目变化都失败。已有脏文件即使前后都显示为 `M`，也通过内容指纹判断是否被再次修改。

检查通过时退出码为 0；发现越界、原有改动被碰触、基线身份不匹配或无法安全判断时，先写出报告，再以退出码 1 结束。

### 3. `finish`：生成交付和证据记录

计划命令形状：

```powershell
uv run scripts/workflow_guard.py finish `
  --baseline "C:\临时证据\start.json" `
  --scope-report "C:\临时证据\scope.json" `
  --result "C:\临时证据\result-input.json" `
  --output "C:\临时证据\delivery.json"
```

`result-input.json` 由 Codex 按示例结构填写，至少包含：

```json
{
  "outcome": "complete",
  "summary": ["更新了README中的启动步骤"],
  "evidence": [
    {
      "stage": "files-changed",
      "status": "passed",
      "detail": "范围检查只发现README.md为本次新增改动"
    }
  ],
  "usage_steps": ["按README中的步骤启动"],
  "remaining": ["未部署，也未执行任何线上操作"],
  "rollback": []
}
```

`finish` 自动合并任务卡、Git 身份、范围检查和人工提供的验证结果。它只登记明确提供且格式合格的证据，不会从本地测试自动推断部署、审核或发布。范围检查失败、证据文件不完整或状态自相矛盾时，不允许输出 `complete`。

## 九、状态模型

计划至少区分以下状态：

```text
已分析
已形成方案
文件已修改
静态检查通过
单元测试通过
构建通过
本地实际启动通过
开发者工具通过
Android真机通过
iPhone真机通过
已部署
已上传
已审核
已发布
线上回读通过
自动化已启用
```

每一项都单独登记 `passed`、`failed`、`not-run` 或 `unavailable`。后面的状态不会因为前一项通过而自动变成通过；外部平台状态必须包含现场来源、核验时间和适用时的版本、提交或构件身份。

## 十、错误处理

| 阶段 | 默认处理 |
| --- | --- |
| 项目路径不存在或基线损坏 | 明确报错并退出，不创建猜测记录 |
| Git 命令不可用 | 只读任务可继续但标记证据受限；修改任务不得声称范围检查完整 |
| 普通测试或命令失败 | 自动收集完整错误，诊断根因并尝试安全替代 |
| 允许范围与当前变化冲突 | 停止后续修改，输出越界清单，不自动扩大范围 |
| 用户已有脏文件发生变化 | 视为范围失败，保留现场，不覆盖、不还原 |
| 数据、安全、隐私或费用不明确 | 失败关闭，明确阻断原因 |
| 缺权限或外部平台不可访问 | 标记 `unavailable`，不把本地状态当成外部证据 |
| 删除、发布或生产写入未授权 | 不执行，并列为需要用户批准的事项 |
| 输出文件无法写入 | stderr 显示简短错误并以退出码 1 结束 |

CLI 不自动恢复、还原、删除、提交、上传或发布，因此范围失败不会引发第二次破坏性操作。

## 十一、API 与限速

本 Skill 的辅助 CLI 不调用外部 API，也不固定连接任何服务，因此没有新增 API 限速、密钥或网络依赖。

需要联网查询时调用现有 Skill，并沿用该 Skill 自己的限速、重试和凭据规则；本 Skill 不重复实现请求逻辑。

## 十二、测试设计

### 样例 1：只读检查不产生项目变化

1. 新建临时 Git 项目并提交初始文件。
2. 在项目外运行 `start`，路线设为 `readonly`。
3. 只读取和分析项目，不写入项目文件。
4. 运行 `scope-check` 和 `finish`。
5. 通过标准：前后 `git status` 完全一致；项目内没有新证据文件；范围报告为通过；交付记录只写“已分析”，不写“已修改”或“已部署”。

### 样例 2：只改 README，并保护用户原有改动

1. 新建临时 Git 项目，提交 `README.md` 和另一个文件。
2. 先人为修改另一个文件，模拟用户原有未提交改动。
3. 运行 `start`，只允许修改 `README.md`。
4. 本次只修改 `README.md`，不碰原有脏文件。
5. 运行 `scope-check` 和 `finish`。
6. 通过标准：原有脏文件指纹不变；本次新增变化只有 `README.md`；范围检查通过；交付准确写“文件已修改”，并明确“未部署、未发布”。

单元测试还应覆盖：只读任务发生写入、允许范围外变化、禁止路径变化、原有脏文件被再次修改、基线提交不一致、畸形结果文件和输出路径不可写。测试全部使用临时目录，不接触真实项目。

## 十三、实现约束

进入 Phase 3 后必须遵守：

- 使用 `apply_patch` 创建 Skill 文件。
- CLI 只使用 Python 标准库和 `argparse`，通过 `uv run` 执行。
- 三个子命令都要求 `--output`，长结果写文件，终端只打印简短状态。
- 所有错误以退出码 1 结束，并尽量先写可诊断报告。

- 实现后按自然语言触发 Skill，并完成上述两个样例和单元测试。
