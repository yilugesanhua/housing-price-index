# 微信小程序版本管理规则

## 目的

使用简单、可检查的版本快照固定微信小程序稳定状态，便于后续回退。Git历史已启用，但不能替代只读稳定版本归档；本规则继续作为发布归档规则保留。

## 目录职责

- `apps/miniprogram/`：小程序唯一源目录，日常代码修改从这里开始。
- `70城小程序技术验证/`：微信开发者工具运行目录，由源目录同步生成。
- `release/miniprogram/`：稳定版本归档目录，不用于日常开发。
- `apps/web/`：Web端；小程序任务不得修改该目录。

每次小程序修改完成后，必须同步到微信开发者工具目录：

```powershell
node scripts/miniprogram/sync-devtools-project.mjs "70城小程序技术验证"
```

同步后检查本次涉及的源文件与目标文件内容一致，再在微信开发者工具中重新编译。

## 版本号

版本号使用 `v主版本.功能版本.修复版本`：

- 修复问题：增加末位，例如 `v0.1.0` 到 `v0.1.1`。
- 增加功能或明显调整：增加中间位，例如 `v0.1.1` 到 `v0.2.0`。
- 达到正式发布标准：使用 `v1.0.0`；后续不兼容变更才增加主版本。

归档文件夹使用 `v版本号_YYYY-MM-DD`，例如：

```text
release/miniprogram/
└── v0.1.0_2026-07-24/
    ├── 小程序源码-v0.1.0.zip
    ├── 版本说明.txt
    └── SHA256.txt
```

## 归档内容

`小程序源码-vX.Y.Z.zip` 必须来自已验证的 `apps/miniprogram/`，并包含运行所需源码、内置数据、云函数源码、项目配置和 `miniprogram_npm/`。

归档不得包含：

- `node_modules/`
- `project.private.config.json`
- 日志、测试截图、临时文件或编辑器缓存
- API Key、Token、密码或其他真实凭据

`版本说明.txt` 至少记录：

```text
版本：v0.1.0
固定日期：YYYY-MM-DD
数据截止月份：YYYY-MM
微信开发者工具版本：
小程序测试结果：
主要功能：
本版变更：
已知问题：
```

`SHA256.txt` 记录源码ZIP的SHA-256，用于确认归档未损坏或被替换。

## 固定版本流程

1. 完成 `apps/miniprogram/` 修改并同步到 `70城小程序技术验证/`。
2. 在微信开发者工具中重新编译并检查相关页面。
3. 运行 `npm.cmd run test:miniprogram`；失败时不得固定版本。
4. 确定新版本号，确认目标归档目录尚不存在。
5. 从 `apps/miniprogram/` 生成排除项清理后的源码ZIP。
6. 填写版本说明并生成SHA-256。
7. 将归档目录设为只读管理；不得覆盖、补改或复用版本号。

## 回退流程

1. 先把当前未归档开发状态另行备份，避免误丢修改。
2. 校验目标版本ZIP与 `SHA256.txt` 一致。
3. 解压目标版本并恢复到 `apps/miniprogram/`。
4. 运行同步命令，覆盖 `70城小程序技术验证/` 中的运行副本。
5. 运行 `npm.cmd run test:miniprogram`。
6. 在微信开发者工具中重新编译，检查首页、城市选择、趋势图和来源页。

回退后如需继续开发，应创建新的修复版本，不得修改原归档目录。

## 管理约束

- 每次修改必须以用户明确确认的范围为边界。范围外的视觉、文案、组件结构、交互、无障碍或技术优化只能记录为建议，不得直接进入候选版本；需要实施时必须先说明原因、影响范围和预期效果并取得明确确认。
- 上线审查发现的非阻断建议不得自动改动既有界面。只有数据真实性、法律合规、明确安全漏洞或无法编译运行等阻断问题可以暂停发布并报告，仍不得擅自扩大修复范围。
- 归档版本只表示小程序代码快照，不替代官方数据来源审计和数据版本记录。
- 同一版本号只能对应一份源码ZIP和一份SHA-256。
- 微信公众平台上传版本号应与归档版本号保持一致。
- 未通过测试或未完成开发者工具检查的状态只能作为临时备份，不能标记为稳定版本。
