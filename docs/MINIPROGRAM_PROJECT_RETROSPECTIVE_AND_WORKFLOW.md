## 一、先说结论

这个项目最终沉淀出的核心能力，不只是一个微信小程序，而是四套可以继续复用的做法：

1. **数据先于页面**：官方来源、口径、解析、全量审计和错误阻断必须先成立，页面才有资格展示结果。
2. **一个对象只有一个身份**：源码、开发者工具副本、候选ZIP、云端数据、线上版本和稳定归档必须分别标识，不能互相代替。
3. **小步修改、分层验证**：局部界面改动只改局部；数据和发布改动按风险逐层扩大验证，不能用“测试很多”替代“测试对了”。
4. **结论必须绑定证据**：已写方案、已改代码、测试通过、真机通过、审核通过、正式发布和自动更新启用是不同状态。

项目最大的成本不在最初页面开发，而在后期纠正数据口径、同步目录、图表兼容、缓存与回滚、候选身份和自动发布证据。后续项目如果从第一天就采用本文的最小工作流，可以少走大部分弯路。

## 四、最重要的成功经验

### 1. 把“官方数据”变成可验证的工程对象

项目最终不是凭页面标题大致相似就采纳数据，而是明确只允许四类官方表：

- 新建商品住宅销售价格指数；
- 二手住宅销售价格指数；
- 新建商品住宅销售价格分类指数；
- 二手住宅销售价格分类指数。

每月必须是70城、每城8种口径、合计560条。解析器变化后要全量重解析，独立审计器再从压缩保存的官方HTML逐表、逐单元格核对。这个设计修复了2018年3月至12月、15城共150条被非目标表覆盖的记录。

可复用原则：**来源白名单、解析器和审计器应相互独立；任何冲突都阻断发布，不能“取最后一个值”。**

### 2. 建立唯一源码和同步副本

正式源目录是 `apps/miniprogram/`，`70城小程序技术验证/` 只是开发者工具运行副本。每次客户端改动都从正式源开始，再运行同步并核对本次文件一致性。

这解决了“代码明明改了，开发者工具为什么没变化”和“两个目录到底哪个是Web”的长期混乱。

可复用原则：**一个目录负责编辑，一个目录负责运行；同步必须由脚本完成，不能两边手改。**

### 3. 用失败关闭保护旧的正确版本

自动更新不是“发现新页面就覆盖线上数据”，而是依次完成来源确认、560条检查、历史零变化、独立审计、错误候选注入、完整包生成、云端全量回读、小程序模拟激活，最后才允许切换指针。

任何一步失败时继续使用上一个已验证月份。回放还故意删除记录和篡改单元格，证明错误候选会在上传或激活前被拒绝。

可复用原则：**新版本只有在证明正确后才能替代旧版本；失败不等于清空或强行更新。**

### 4. 把发布状态拆开登记

本项目后期明确区分：

`方案已批准 -> 代码已实现 -> 本地测试 -> CI -> 候选构件 -> 开发者工具 -> Android -> iPhone -> 上传 -> 审核 -> 发布 -> 线上回读 -> 稳定归档`

这避免了“版本号已经改了，所以线上就是这个版本”“开发版能定位，所以正式版也有权限”“12个月回放通过，所以真机和审核也通过”等错误推断。

可复用原则：**每个状态单独留证，前一步不能推导后一步。**

## 五、Bug、踩坑和绕路总表

### A. 项目管理与协作

| 现象 | 根因或绕路 | 后续固定规则 |
| --- | --- | --- |
| 项目前期已经大量修改，Git直到2026-07-27才正式初始化 | 早期版本、回退点和变更原因难以追踪 | 新项目在第一次代码修改前初始化Git、提交基线并确认忽略项 |
| 用户担心两个会话同时改会冲突 | 多个会话共享同一工作区，可能覆盖同一文件或读到中间状态 | 同一工作区同一时间只保留一个“写入者”；并行任务只做独立只读研究，代码并行必须使用独立分支/工作树 |

| 166份会话中有155份子任务记录，日志约4.09 GB | 并行和自动续跑产生大量重复上下文，增加检索和状态漂移成本 | 子任务只用于可独立验收的工作；结果必须回到主任务的单一清单，完成后不继续复制全项目上下文 |

### B. 界面、图表和交互

| 现象 | 根因或绕路 | 后续固定规则 |
| --- | --- | --- |
| 筛选框大小不一 | 列宽、控件宽度和盒模型没有统一 | 固定网格轨道、`width: 100%`、稳定高度和`box-sizing`，最长文案也要实测 |
| 顶部筛选/导航滚动后消失 | 原生小程序页面中的`position: sticky`表现不可靠 | 使用滚动阈值切换固定定位，并用等高占位防止页面跳动 |
| 图例虚线与实际曲线不一致 | 图例样式和图表序列样式分别维护 | 图例和曲线从同一个序列配置生成，并对每个系列做截图或像素级回归 |
| 添加城市按钮越缩越小，文字难看清 | 只为挤空间而压缩控件，没有守住文字和触控下限 | 先重排布局，再缩小控件；文字完整、稳定尺寸和可点击面积是硬条件 |
| 图表内容随曲线高度出现遮挡、城市数显示不稳定 | 动态绘制内容影响容器或覆盖层布局 | 图表、图例、提示和计数采用稳定容器尺寸，动态内容不得改变外围布局 |
| Windows开发者工具三张图异常 | wx-f2在桌面模拟器的轴标签裁切、Tooltip和二次`changeSize`转换存在差异 | 桌面模拟器和手机使用明确的兼容分支；桌面问题不能推断真机问题，反之亦然 |
| iPhone图表空白，修好后又模糊 | “构建npm”可能重建`miniprogram_npm`并引入缺失运行时；Canvas清晰度还受像素比和编译缓存影响 | 同步自包含运行包、递归检查`require`、清编译缓存、重新连接iPhone和Android；空白与清晰度分别验收 |
| 代码检查通过但开发者工具预览失败 | 实际错误是登录凭证失效、代理端口无服务或网络重置，不是项目编译错误 | 先读开发者工具日志，分清代码、登录、代理、网络和平台问题，再决定是否改代码 |
| 连续做了三版大改预览仍不满意，最后全部删除 | “大改”的结构目标没有先量化，直接复制完整项目并写代码，预览成本过高 | 先确定3到5个必须明显变化的区域，先做静态整页稿/低成本原型；方向确认后再建可运行预览 |

| 现象 | 根因或绕路 | 后续固定规则 |
| --- | --- | --- |

| 重复做多组相同36个月回放耗时很长 | 测试数量增加，但覆盖风险没有变化；三组合计核心耗时约4小时14分 | 先按变更风险选一组有代表性的回放；相同代码和场景重复跑的边际收益很低，也不能替代真机和平台证据 |

### G. 状态、文档和工具判断

| 现象 | 根因或绕路 | 后续固定规则 |
| --- | --- | --- |
| 文档中的当前版本文字落后于源码 | 多处人工维护同一事实 | 机器可读版本只有一个源；其他文档只写带日期快照并明确可能过期 |
| 旧版本测试被拿来证明新候选 | 版本号、提交和构件哈希未强绑定 | 任何客户端构件变化都生成新候选并使旧外部证据失效 |
| “规范已写入”被误解为“功能已实现” | 目标规则和实施状态混在同一结论 | 权威规范定义应当怎样，实施登记只记录现在做到哪一步 |
| GitHub页面用户能看，终端却说看不了 | CLI未登录且匿名API遇到限流，被误判为资源不存在 | 先检查`gh auth status`和请求限流；浏览器登录态、CLI登录态和匿名API是三种状态 |
| 插件显示已安装/启用，但当前任务找不到 | 新装插件不会动态注入已经运行的任务 | 区分安装、启用、新任务可见和实际调用成功；安装后重启并新建任务验证 |

## 六、哪些做法不应机械复制到下一个项目

1. **不要一开始就复制本项目全部治理复杂度。** 本项目的数据会自动写入生产且影响所有用户，所以需要双开关、撤销、回滚、迁移和大量故障测试。普通静态小程序不必先搭这么重的系统。
2. **不要用回放次数代替风险覆盖。** 先列出本次改动可能破坏什么，再选最小但足够的测试。相同场景重复100次也证明不了iPhone、审核或权限。
3. **不要为看设计方向先复制整个项目三次。** 先用整页静态稿确认结构差异，再实现一份独立预览。
4. **不要让历史报告变成第二套当前规范。** 历史报告只证明当时的提交和环境。
5. **不要把所有逻辑都迁入共享层。** 只有建立跨平台固定输入、独立期望和逐值一致测试后，才迁移排名、涨平跌或累计计算。
6. **不要把“能自动跑”写成“无人值守”。** 没有通知接收、确认超时和恢复闭环时，只能称为有人监督自动化。

## 七、后续微信小程序开发的标准做法

### 1. 新项目最小文档集

开始时只建够用的文件，后续按风险增加：

| 文件 | 只负责什么 |
| --- | --- |
| `AGENTS.md` | 修改边界、技术基线、标准命令和完成条件 |
| `PRODUCT.md` | 用户、范围、明确不做什么、平台差异 |
| `DATA_CONTRACT.md` | 仅数据项目需要：来源、字段、缺失、校验、修订 |
| `DESIGN.md` | 视觉令牌、组件、交互和响应式/小程序约束 |
| `ACCEPTANCE.md` | 什么证据才算完成 |
| `IMPLEMENTATION_STATUS.md` | 只在规范目标明显多于当前实现时建立，记录差距，不复制规范 |
| `RELEASE_HANDOFF.md` | 当前候选身份、平台操作、验证和未完成事项 |

### 2. 每次任务开始前

1. 用一句话写清用户真正要得到的结果。
2. 明确只允许修改哪些目录、页面和功能，列出禁止修改项。
3. 读取项目规则、当前源码、版本源和相关验收条款。
4. 执行`git status`，记录用户已有改动；有重叠时先理解，不能覆盖。
5. 判断任务类型：只读、界面、功能、数据、云端还是发布。
6. 只有结构性设计、外部写入、删除、发布或会明显改变结果的选择才先等用户确认。

### 3. 实施时

1. 一次只解决一个明确问题或一个紧密相关批次。
2. 优先沿用现有组件、类型、令牌、脚本和测试。
3. 小程序客户端改动同时递增版本、同步开发者工具副本并核对文件。
4. 数据生成物只由脚本产生，不手工改JSON冒充可复现结果。
5. 出现未知错误时先收集完整阶段证据，再改最小根因；不要连续追加零散日志或猜测性补丁。
6. 需要用户操作时，一次只给当前一步，并写清成功标志。

### 4. 按风险分层验证

| 改动 | 最低验证 | 还必须补充 |
| --- | --- | --- |
| 文案或单点样式 | 相关静态/快照检查，开发者工具完整页截图 | 手机尺寸、文字不截断、未授权区域无变化 |
| 布局、图表、触摸交互 | 小程序测试、同步、开发者工具实操 | Android+iPhone；必要时Windows开发者工具单独兼容 |
| npm依赖或图表库 | 递归运行包依赖检查、清编译缓存 | Android+iPhone重新连接，空白、清晰度、旋转、触摸Tooltip |
| 定位/隐私接口 | 拒绝、超时、缓存过期和手动回退测试 | 微信后台权限/隐私指引、体验版和正式版现场证据 |
| 解析器/数据口径 | 全量重解析、独立逐值审计、错误注入 | Web和小程序重新生成，修订账本与来源身份 |
| 远程数据/缓存 | 哈希、临时落盘、回读、原子激活、中断和重启 | 弱网、存储失败、双真机、旧缓存与安全回退 |
| 云端发布/回滚 | 隔离环境全链路、生产未触碰证明 | 双开关、同提交CI、受保护环境、写后全量回读和监测 |
| 正式发布 | 候选ZIP/提交/版本绑定 | 开发者工具、双真机、上传、审核、线上回读和归档分别登记 |

### 5. 完成时的状态用语

只使用有证据的词：

- “代码已修改”：文件确实变化。
- “本地测试通过”：列出命令、数量和提交/工作区身份。
- “开发者工具通过”：实际重新编译并操作。
- “真机通过”：写明Android或iPhone，不能互相代替。
- “已上传/已审核/已发布”：必须是微信平台对应状态。
- “线上可用”：正式版现场操作和正式数据回读通过。
- “自动更新已启用”：生产开关现场回读及完整门槛通过。

## 八、候选个人工作流 v0.1

根据本项目中用户反复强调的习惯，可以总结为一套“**定界、盘点、方案、小步、分层验证、证据交付、复盘固化**”七步工作流。

这套流程的特点是：用户不需要懂代码；Codex在授权范围内主动完成；高风险和结构性变化先确认；每个结论都有证据；发现的规则会进入下一次任务，而不是只留在聊天里。

### 第1步：定界

输出一张任务卡：

```text
本次目标：
只允许修改：
明确不修改：
成功标准：
需要用户操作或批准的事项：
```

只读检查就不写文件；用户说“只改小程序”就不碰Web和共享层；用户说“先出方案”就停在方案。

### 第2步：盘点

Codex自动读取项目规则、当前实现、Git状态、版本源、已有测试和相关历史教训，先区分：

- 当前源码事实；
- 用户已有未提交改动；
- 历史报告；
- 外部平台当前状态；
- 能现场验证和不能现场验证的部分。

### 第3步：方案

默认只推荐一个最简单、安全、稳定、成本合理的方案，并说明主要取舍。只有以下情况先等确认：

- 页面结构或整体风格明显改变；
- 会修改用户未授权区域；
- 删除、覆盖、付费、发布或生产写入；
- 两种方案会得到明显不同的产品结果。

### 第4步：小步实现

按风险最小的顺序修改，一次只做一个问题或一组强相关问题。每步都保留旧的安全状态，不做无关重构，不为过测试改变正确需求。

### 第5步：分层验证

先跑最接近改动的快速测试，确认根因后再扩大到完整检查、开发者工具、真机、隔离云端或正式平台。失败就停在当前层，保留证据并从根因修复。

### 第6步：证据交付

最终输出固定包含：

```text
结论：现在到了哪个真实状态
做了什么：面向用户的变化
改了什么：文件和版本
验证了什么：命令、页面、设备、平台和结果
怎么使用：启动或操作步骤
还缺什么：未验证范围、需要用户完成的事项
怎么回退：适用时给出安全回退点
```

### 第7步：复盘固化

每次发现可复发问题时，按顺序判断是否需要：

1. 增加防复发测试；
2. 更新已有权威规范；
3. 更新验收标准；
4. 更新执行/交接说明；
5. 只有跨项目反复适用时，才提升为个人Codex Skill。

### 三类任务的默认行为

| 用户说法 | 默认行为 |
| --- | --- |
| “看看、检查、审核、先出方案” | 只读分析，不修改、不安装、不发布；如用户明确禁止测试，也不运行测试 |
| “修改、修复、创建、安装” | 在指定范围直接完成依赖、修改和验证，不只给建议 |
| “上线、发布、打开开关、删除” | 先核对精确目标、影响和回退；仅在明确授权和门槛满足后执行 |

### 推荐的用户输入模板

以后可以直接把下面内容交给Codex，不必写技术细节：

```text
项目位置：
这次想达到的结果：
只允许改动：
明确不要改：
先出方案还是直接执行：
成功后我希望看到：
是否允许外部操作（上传、发布、云端写入）：
```

如果用户没有填全，Codex应先从项目中安全判断；只有缺失信息会明显改变结果或带来不可恢复操作时，才一次询问最关键的问题。

## 九、是否适合做成个人Skill

**适合。用户已完成用途、输入输出、频率、错误处理、复用能力、安装位置、辅助脚本和测试样例确认；Skill现已创建、安装并通过本地自测。**

这套流程已经在一个真实、复杂、跨Web/微信/数据/云端的项目中反复出现，具备复用价值。Skill目标不是“自动替用户做任何项目”，而是：

> 在现有代码项目中，先定界和盘点，再按风险小步实施、分层验证，并用准确状态和证据完成交付；遇到可复发问题时同步固化测试、规范和验收。

## 十、交给后续维护人员的一页清单

开始任何小程序修改前，维护人员至少确认：

- [ ] 我正在修改`apps/miniprogram/`，不是同步副本或稳定归档。
- [ ] 我已看过Git状态并保留他人改动。
- [ ] 本次修改范围已经明确，没有顺带改未授权页面。
- [ ] 客户端构件变化会同步递增`version.js`。
- [ ] 改完会运行同步，并核对正式源与开发者工具副本。
- [ ] 数据来自白名单官方表，生成文件不是手工修改。
- [ ] 图表/npm改动会清编译缓存并重做Android和iPhone。
- [ ] 数据/缓存改动覆盖失败、中断、重启和旧版本保留。
- [ ] 云端演练只写隔离前缀，能证明生产指针未触碰。
- [ ] 上传、审核、发布、线上可用和自动更新启用分别留证。
- [ ] 最终交付说明仍未验证的范围，不把旧证据套给新版本。

只要其中任何一项与本次任务相关却无法确认，就不能把当前候选写成“已完成”或“已正式可用”。
